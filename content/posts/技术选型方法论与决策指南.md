技术选型大概是研发团队里决策影响最久、又最容易被草率对待的事情之一：一个框架或中间件的选择，往往要在未来几年里持续付出成本，而想推翻重选时，业务和代码都已经长在上面了。既然代价这么大，就值得把它当成一个流程来走，而不是靠一两个人当场的印象定下来。下面这套方法按"原则 → 流程 → 清单 → 误区 → 记录"的顺序展开，可以直接用于下一次选型。

## 选型要看的五个维度

### 业务驱动

技术服务于业务，这在选型时是硬约束而不是口号。先定义清楚：要解决什么业务痛点，未来一到三年的业务预期要求技术往哪个方向走。为不存在的规模做准备是过度设计，对明摆着的增长视而不见则是短视。

### 成熟度与社区

- 文档：是否完整、清晰、跟得上版本。开源项目的文档质量，基本能反映项目的治理水平。
- 社区：提交与 Issue 的活跃度、问题响应速度、周边生态（插件、三方库）是否够用。
- 案例：同类场景的落地先例。参考价值与规模有关——大厂案例往往业务形态差异太大，同体量团队的实践更值得看。

### 团队匹配

- 学习曲线：团队上手成本有多高，是否值得为此安排培训。
- 人才市场：该技术栈的人好不好招。招不到，意味着长期只能靠现有团队硬扛。
- 技术栈统一度：每引入一种新技术栈，跨项目协作和人员轮岗都会多一分成本。这是选型里最容易被低估的隐性成本。

### 成本与收益

从整个生命周期算账，而不是只看开发阶段的体验：

- 开发成本：能否提升开发效率，提升多少。
- 运维成本：部署、监控、排障的难度。
- 迁移成本：替换存量技术时要付出什么。这部分常在选型时被忽略，真正落地时才暴露。

### 可控性

- 开源协议是否友好（MIT、Apache 2.0），必要时能否自己读源码定位问题、打补丁。
- 商业产品要评估供应商的稳定性与支持力度。
- 无论开源还是商业，都要想清楚退出路径：万一要换掉它，数据和代码能不能搬走。

## 选型流程

把选型当成一个小项目来管，七个步骤：

1. 明确需求——功能性需求（高并发、实时性）和非功能性需求（可用性、安全性）分开列清楚，调研时不容易被候选方案带偏。
2. 市场调研——通过技术博客、GitHub、社区搜一轮，列出 3–5 个候选。注意信息来源的多样性，别只看到热度最高的那一个。
3. 初步筛选——按上述维度快速淘汰明显不合适的，保留 2–3 个进入下一轮。
4. 深入评估——针对核心业务场景搭 PoC 原型验证，该做基准测试就做。特性对照表只能说明"有没有"，真实负载才能说明"行不行"。
5. 决策评审——把评估结果交给技术委员会或资深同事评审，输出选型报告。评审的意义在于让决策多一双眼睛，而不是走形式。
6. 小范围试点——先在非核心模块试运行，验证文档完善度、实际踩坑数量和团队的上手手感。
7. 全量推广——把用法、规范和已知的坑沉淀成文档，再铺开。

## 评估清单

打分时可以参照下面的维度，权重是示例值，按团队情况调整：

| 维度 | 关注点 | 权重 (示例) |
| :--- | :--- | :--- |
| 功能满足度 | 核心功能是否开箱即用，扩展性如何 | 40% |
| 性能与稳定性 | 吞吐量、延迟、资源占用、长期运行稳定性 | 20% |
| 文档与社区 | 官方文档质量、FAQ、社区活跃度、Bug 修复速度 | 15% |
| 易用性 | API 设计是否优雅、配置是否简单、工具链是否完善 | 10% |
| 运维友好度 | 监控指标、日志清晰度、部署复杂度 | 10% |
| 安全性 | 漏洞响应机制、权限控制、加密支持 | 5% |

打分时注意区分"团队已经亲手验证过的"和"只是从文档上读来的"——前者的判断权重应当更高。

## 常见误区

- 简历驱动开发：为了简历好看而选技术，收益归个人，成本由团队长期承担。
- 跟风：热门不等于合适。很多系统根本没有微服务、容器编排的需求，却被"大家都上了"推着走。
- 造轮子：开源方案已覆盖大部分需求时，自研意味着这些功能的维护责任从此归你，而且没有社区帮你持续改进。
- 只评估开发体验：开发时顺手，不等于运维时省心。部署、监控、排障的长期成本，应该和上手体验放在同一杆秤上。

## 决策记录：ADR

选型结论确定后，值得花十分钟把决策过程写下来，形成一份架构决策记录（Architecture Decision Record, ADR）。原因很实际：三个月后，当初参与讨论的人不一定记得清理由；半年后，团队里可能已经没人说得清"为什么是它"。ADR 至少包含：

- 标题：采用 [技术] 作为 [场景] 的解决方案
- 状态：提议中 / 已采纳 / 已废弃
- 背景：当时面临什么问题，为什么需要引入新技术
- 决策：选了什么；没选什么、为什么——把被否掉的方案和理由写进去，这部分信息量最大
- 后果：正面影响是什么，以及引入了哪些新的复杂性、限制

状态一栏不必只写"已采纳"。被替代、被废弃的决策同样值得保留——几年后有人提出"要不要换成 X"时，当年的记录能直接告诉他，这次换和上次换有什么不同。

流程保证不了每次都选对：信息永远不完整，判断总有风险。它保证的是另一件事——决策有记录，理由可回溯。几个月甚至几年后回看，无论当初选对选错，都能说清楚当时为什么这么定；这样的记录攒多了，就是团队现成的一份选型经验库。
